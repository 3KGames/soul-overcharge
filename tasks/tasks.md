### Фактические значения из текущих ассетов

Параметры движка берутся из `Assets/Game/Data/Engine.asset`
(`volume: 1.4`, `pistonStroke: 0.08`, `pistonMaxSpeed: 0.02`,
`inertiaCoef: 0.08`, `idleRPM: 750`, `stallRPM: 500`, `a: 1`, `b: 1`, `c: -1`):

- `Inertia = inertiaCoef * volume` = `0.08 * 1.4` = **`0.112 кг*м^2`**
- `MaxOmega = 1000 * П * 0.02 / 0.08` = **`785.398 рад/с`**
- `MaxRPM` = **`7500 об/мин`**
- `PeakTorque = 80.48 Н*м` (считается при `rpmNorm = 1`, то есть на `MaxOmega`)
- `ClutchMax = 80.48 * 1.5` = **`120.72 Н*м`**
- `ClutchProportion` при `clutchError = 16.7` = **`7.23 Н*м на рад/с`**
- `ClutchProportion` при `clutchError = 0.1` (текущее состояние ассета) =
  **`1207 Н*м на рад/с`**

Устойчивость петли — `dt < 2 * Inertia / ClutchProportion`:

| `clutchError` | `ClutchProportion` | предельный `dt` | фактический `dt = 0.02` | итог |
|---|---|---|---|---|
| `16.7` | `7.23` | `0.031 с` | `0.02 с` | устойчиво, запас ×1.55 |
| `0.1` | `1207` | `0.000186 с` | `0.02 с` | **неустойчиво, запас ×0.009** |

| кадр | RPM | действие |
|---|---|---|
| 1 | 7500 | порог достигнут, срез запущен, момент 0 |

## Открытый вопрос — `AutoShiftTick` и лаг в один кадр

Раньше это было записано как баг. После чтения кода вывод другой.

`Tick` вызывается из `DriveCarState` ДО `UpdateAngularSpeed`, поэтому
`UpdateAutoShift` читает `RPM` прошлого кадра. Но `EndStep` в конце того же кадра
публикует через `RpmChanged` ровно это значение. То есть сдвига на кадр нет:
решение принимается по последнему известному обороту, а переключение применяется
на следующем кадре — это минимальная задержка без перестановки стейта.

Сигнатура уже документирует это: «Обороты для решения берутся прошлые — лаг в один
кадр (20 мс) на переключение не влияет». На 20 мс решение об автопереключении
не меняется.

Чтобы читать обороты текущего кадра, пришлось бы перенести `Transmission.Tick`
после `UpdateAngularSpeed` и пересчитать момент сцепления уже с новой передачей.
Это перестановка горячего пути ради 20 мс. **Рекомендация: код не трогать, считать

### Как устроено ограничение сцепления

Потолок берётся не на силе, а на моменте:

```
maxBrakeTorque = maxLongitudinalGrip * wheelRadius   // 26000 * 0.288 = 7488 Н*м
appliedBrake   = Mathf.Clamp(brakeTorque, 0, maxBrakeTorque)
netTorque      = driveTorque + roadFeedbackTorque - brakeDir * appliedBrake
```

Отсюда следует, что колесо не может встать по построению. В равновесии
`roadFeedbackTorque == appliedBrake`, значит `|tireForce| == appliedBrake / R`,
а она по потолку не превышает `maxLongitudinalGrip`. Для полного проскальзывания
проскольжение должно было бы дойти до −v, то есть потребовать силу в
`v * tireStiffness` — в 5.4 раза больше потолка при 100 км/ч.

### Расчёт без запуска

Эффективная масса = 880 + 40.8 = 920.8 кг.

- Полный `Brake`: сила 26 000 Н, замедление **28.2 м/с²** (цель 25–30) ✓
- Насыщение: `brakeTorqueNm: 12000` при потолке 7488, поэтому педаль
  насыщается на 62% хода — ниже торможение линейное, выше плоское.
- Остановка со 100 км/ч (27.78 м/с): `v²/2a` = **13.7 м**.
- Проскальзывание в равновесии: −26 000 / 5000 = **−5.2 м/с**, пятно

- Дрифт: 4000 Н·м → 13 889 Н → 15.1 м/с², ниже потолка, торможение

### Задача 22 — холостые толкали машину

Пользователь обнаружил в play-mode: машина едет сама без газа. Баг был
не связан с задачей 20 — `torqueDrive` не менялся, а проявился, как только
торможение заработало и стало можно трогаться и останавливаться.

**Корень.** `UpdateEngagement` не смотрел на газ: сцепление раскатывалось
до 1.0 чисто по времени. На месте при полном сцеплении `angDelta = IdleOmega`,
`CalculateClutchTorque` упирался в потолок `ClutchMax`, и П-регулятор холостых
(он держит 750 об/мин добавлением газа) продавливал момент на колёса.

Расчёт на текущих значениях, 1-я передача, газ 0:

| Величина | Значение |
|---|---|
| `PeakTorque` при `MaxOmega` | 110.3 × 0.9 = 99.3 Н·м |
| `ClutchMax` = PeakTorque × 1.5 | 148.9 Н·м |
| `ClutchProportion` = 148.9 / 16.7 | 8.92 Н·м на рад/с |
| `ClutchProportion × IdleOmega` | 700 → упирается в потолок 148.9 |
| `torqueDrive` | 148.9 × 12.61 × 0.9 = 1690 Н·м |
| Сила на колесе | 1690 / 0.288 = 5868 Н |
| Разгон без газа | **6.4 м/с²** |

**Исправление** в `TransmissionService`:

1. `_engagement` инициализируется `0f`, а не `1f` — на месте схватывать нечем.
2. `UpdateEngagement` принимает `throttle`, цель сцепления = газ:
   `Mathf.MoveTowards(_engagement, throttle, rate)` вместо
   `Mathf.Clamp01(_engagement + rate)`. MoveTowards нужен, чтобы одинаково
   и набирать, и отпускать сцепление при сбросе газа.
3. `Tick` передаёт `throttle` в `UpdateEngagement`.

Проверено, что двигатель на разомкнутом сцеплении не заглохнет и не
перекрутится: равновесие холостых держит П-регулятор с очень малой
невязкой — момент трения на 78.5 рад/с равен 2 + 0.035 × 78.5 +
0.000034 × 78.5² = 4.96 Н·м, и набрать его governor может при газе
порядка 5.5e-6, то есть отклонение от 750 об/мин меньше 1e-4 рад/с.

На скорости выше `LaunchSpeed` (2 м/с) поведение не меняется: там
сцепление по-прежнему полностью сцеплено, газ на него не влияет.
Трогание становится управляемым газом вместо захвата П-регулятором.

### Задача 23 — осцилляция на удержании тормоза

Пользователь: при удержании тормоза машина осциллирует между положительной
и отрицательной скоростью. Проявилось после задач 20–22.

**Корень.** Тормоз — сухое трение: модуль момента не зависит от вращения
колеса. `appliedBrake` = 7488 Н·м применялся на малом вращении без
ограничения, и за один сабстеп (0.002 с при 10 сабстепах и dt 0.02) омега
проносилась через ноль:

| Шаг | Значение |
|---|---|
| Δω за сабстеп = 7488 / 1.1 × 0.002 | 13.6 рад/с |
| `brakeDir` после пересечения нуля | меняет знак |
| `tirePatchSpeed` при `v ≈ 0` | ±3.92 м/с |
| `tireForce` | ±19 600 Н |
| ускорение кузова | ±21 м/с² |

Колесо скачет между ±13.6 рад/с, и через `tireForce` это уходит в кузов —
предельный цикл. На ходу не проявляется: чтобы догасить омегу модуль должен
превысить 7488 Н·м, то есть омега должна упасть ниже 13.6 рад/с, что
соответствует пятну качения меньше 3.9 м/с. Поэтому осциллировала только
стоянка.

**Исправление.** Вклад тормоза ограничен моментом, который ровно гасит текущую
омегу и не переворачивает её:

```csharp
float brakeCap = Mathf.Abs(DrivenWheelsOmega) / subDt * WheelInertia;
float brakeThisStep = Mathf.Min(appliedBrake, brakeCap);
float netTorque = driveTorque + roadFeedbackTorque - brakeDir * brakeThisStep;
```

Это статическое трение в дискретной форме: довести колесо до нуля можно,
начать крутить его в другую сторону — нельзя. `driveTorque` не ограничен,
поэтому трогание под газом и работа коробки не затронуты.

**Поведение после правки.** На стоянке омега зажата около нуля, поэтому
`tireForce = -v × 5000`, замедление `5.43 × v` м/с², постоянная времени
0.18 с. Скорость затухает в ноль без смены знака. На ходу `brakeCap` не
срабатывает, поведение не меняется.

**Попутно исправлено.** Метод возвращал силу последнего сабстепа. На ходу
разницы нет (в равновесии момент равен нулю, омега постоянна, все сабстепы
дают одно значение), но на стоянке под тормозом омега колеблется 0..8 рад/с
внутри кадра, и возврат последнего сабстепа давал кадрозависимое дрожание
силы от −15 000 до −3700 Н — ровно там, где торможение должно быть самым
плавным. Теперь возвращается среднее по сабстепам.

**Проверка отсутствия обратного хода.** На стоянке `tireForce = -v × 5000`
всегда отрицателен при `v > 0`, то есть положительный толчок невозможен.
Интеграция кузова линейна: `v_new = v × (1 - 5.43 × 0.02) = 0.891 × v`,
множитель в (0, 1), перелёта через ноль нет. Воздушное сопротивление
`0.376 × v²` тоже всегда против скорости.

### Задача 24 — AccelerationGraphWindow не видел правки ассетов

Пользователь: «хочу чтобы при смене любого из ассетов или его полей
AccelerationWindow Graph обновлялся».

**Диагноз оказался не тем, чего ждали.** Окно уже обновлялось каждый кадр:

на каждом событии. Кнопки обновления не было и не требовалось. Настоящая
причина — **снимок полей**.

`EngineModel` копирует все поля `EngineSO` в конструкторе, а
`EngineService` поверх этого кэширует `PeakTorque`. Окно держало
`_evalEngine` и обнуляло его только при смене **ссылки** на ассет
(`ResetRangesToData`), но не при изменении **полей**:

| Источник | Данные | Реакция на правку |
|---|---|---|
| снимок `EngineModel` | `PeakTorque`, `EngineMass`, `IdleOmega`, `MaxOmega`, `MaxRPM`, `CalculateTorqueAt`, `CalculateFrictionAt` | **не было** |
| прямо из SO | `IdleThrottleGain`, всё `DrivetrainSO`, `TransmissionSO`, `CarPhysicsData` | было |

**Часть 1 — снимок убран.** `GetEvalEngine()` больше не кэширует и всегда
строит `EngineService` заново. Двигатель строится один раз на событие
`OnGUI` в `OnGUI` и передаётся параметром вниз: `GetCurves` → `BuildCurves`

конструкторов на кадр было бы ровно то, от чего защищал прежний комментарий.

**Часть 2 — кэш кривых.** Считались 256 точек × 5 передач = 1280
вычислений на каждое событие Layout и Repaint, то есть ~2560 на кадр,
каждое с `Mathf.Pow` и делениями. Добавлен кэш:

- `ComputeCacheKey()` — хеш содержимого четырёх ассетов через

  `_selectedGearIndex`.
- `GetCurves(key, engine, out rebuilt)` — при совпадении ключа отдаёт
  `_cachedCurves`, при расхождении пересобирает.
- Безусловный `Repaint()` в конце `OnGUI` убран, `Repaint()` вызывается
  только при `rebuilt`. В простое окно не перерисовывается и не считает
  ничего.
- `Undo.postprocessModifications` и `Undo.undoRedoPerformed` (подписка в
  `OnEnable`, отписка в `OnDisable`) будят окно при правке ассета в

1. Первая версия `ComputeCacheKey` писала результат в `_cacheKey`, а

   истинно, кэш не сбрасывался бы **никогда**. Разведены `_builtKey`

2. Первая версия мемоизизовала хеш по `Time.frameCount`. Если счётчик кадров

   риск на критичном пути. Мемоизация убрана: безусловный `Repaint` уже
   снят, поэтому в простое `OnGUI` не вызывается и хеш не считается.

**Проверено статически:** все вызовы `EvaluateAccelInGear` / `GetAccelForGear`
/ `BuildCurveForGear` / `BuildCurves` переведены на новые сигнатуры, старых
вызовов не осталось, скобки 75/75, скобочки 302/302.

| Ошибка | Реальная причина |
|---|---|
| CS0407 ×2 | делегат возвращает `UndoPropertyModification[]` — весь массив |
| CS1061 | поля `targetObject` у `UndoPropertyModification` нет |

**Как надо было проверить.** Рефлексия не годится: `UnityEditor.dll` не
грузится вне редактора, `Assembly.GetTypes()` кидает

Отсюда же видно, почему `targetObject` не искался: структура хранит только

**Итог по пробуждению.** Разбор `modifications[]` удалён вместе с

**Третий источник пробуждения.** Добавлен `EditorApplication.projectChanged`:

### Задача 25 — единицы окна, границы по умолчанию, лишняя кнопка

Пять пунктов от пользователя. Пункт «All Gears по умолчанию» выполнен уже
был: `PlotMode _plotMode = PlotMode.AllGears`, править не пришлось.

**`-1` — буквальное значение, а не признак «авто».** Смысл зафиксирован
устным ответом пользователя, вариант A из двух предложенных. Вариант B
(«-1 значит авто») отвергнут: он противоречил требованию «Auto Y не влияет
на Y Min», потому что автоподбор влиял бы на низ ровно через этот -1.

**Границы скорости в км/ч, физика в м/с.** Поля `Speed Min`/`Speed Max`
вводятся в км/ч, хранятся в м/с. Конвертация только на границе поля и в
подписях — внутри вычислений её быть не должно, иначе график и формулы
разъезжаются. Единая константа `KmhPerMs = 3.6f`.

Переведены подписи: ось X и `Speed:` в курсоре. `Accel` (м/с²) и RPM
оставлены как были — это не скорость, и в км/ч они бы не переводились.

Значения по умолчанию: `Speed Min` = -1 км/ч, `Speed Max` = 252 км/ч
(= прежние 70 м/с, физическое значение не менялось), `Y Min` = -1 м/с²,
`Y Max` = 50 м/с².

**Участок левее нуля безопасен.** `EvaluateAccelInGear` зажимает
отрицательную скорость в 0, поэтому при `Speed Min` = -1 первые точки
считаются как ноль, а не дают мусор в физике.

**`Auto Y` больше не трогает низ оси.** Раньше блок автоподбора писал и
`_yMin`, и `_yMax` по данным кривых, то есть перезаписывал низ оси каждый
кадр. Теперь автоподбор двигает только верх, а `Y Min` стал полем,
доступным всегда. `Y Max` остался под `Auto Y`.

**Побочный эффект, который стоит знать:** при данных ниже `Y Min` они
обрезаются. Раньше низ подстраивался сам. Это цена требования «Auto Y не
влияет на Y Min», и она осознанная.

**Регресс, найденный пользователем сразу после:** сломался cursor readout.
Окошко появлялось, но не двигалось за мышью.

Причина — прямое следствие снятия безусловного `Repaint()` в задаче 24.
Подсказка рисуется по `Event.current.mousePosition` в событии Repaint, и
единственной причиной, по которой окошко шло за курсором, был как раз тот
безусловный `Repaint`: он перерисовывал окно каждый кадр. Без него окно на
движение мыши не отвечает, и последний нарисованный кадр с подсказкой
висит на старом месте.

Исправление: `Repaint()` запрашивается на `MouseMove` и `MouseDrag`, но
только при включённом `_showCursorReadout`. На самом Repaint вызова нет,
цикла не возникает. Кэш кривых при этом не тронут: дорогая пересборка
по-прежнему заперта на ключе, восстановлена только перерисовка. При
выключенной подсказке окно снова полностью засыпает.

**Урок на будущее:** безусловный `Repaint` в окне с курсорной подсказкой —
это не «грязный» код, а неявная зависимость. Снимать его можно только
вместе с явным запросом перерисовки на движение мыши, иначе ломается
интерактив.

Попутно убрано поле `CurveData.MinY`: после переработки автоподбора оно
больше не читалось, но накопление минимума по 256 точкам на кривую
оставалось. Снято вместе с ним.

строки ниже и никакого состояния не несла.
